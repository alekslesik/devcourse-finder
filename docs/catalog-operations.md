# Регламент публикации каталога

## 1. Назначение и ответственность

Регламент описывает проверяемую публикацию реального каталога DevCourse Finder и закрывает требование MVP-DATA-02. Его выполняет оператор, имеющий доступ к файлу каталога, приложению и резервному копированию PostgreSQL.

Оператор отвечает за проверку источников и итоговый diff. Приложение отвечает за структурную валидацию, атомарность импорта и запись снимков до и после успешной операции.

Для каждой production-публикации оператор создаёт отдельную копию [протокола публикации](./catalog-publication-record.md) во внешнем хранилище release-артефактов и заполняет её по ходу выполнения регламента. Пустой шаблон в репозитории сам по себе не является подтверждением публикации.

## 2. Обязательные условия

Перед публикацией необходимо убедиться, что:

- рабочее дерево и release commit известны;
- Compose-стек запущен, а `GET /health/ready` возвращает HTTP 200;
- файл подготовлен в формате `catalog.Dataset` и не содержит секретов;
- у каждой публикуемой программы вручную проверены источник, тариф, цена, статус набора и дата проверки;
- устаревшее или неподтверждённое значение не выдается за точную цену;
- `CATALOG_OPERATOR` содержит устойчивый идентификатор оператора, например корпоративный логин;
- создана резервная копия непосредственно перед изменением production-каталога.

Команды ниже предполагают запуск из корня репозитория. Путь к файлу задаётся один раз:

```sh
export CATALOG_FILE="$PWD/catalog.production.json"
export CATALOG_OPERATOR="operator-login"
test -r "$CATALOG_FILE"
```

Не используйте общее значение `local-operator` в production. Не добавляйте production-файл в Git, если он содержит ещё не опубликованные партнёрские адреса или иные закрытые данные.

## 3. Проверка источников

Для каждой записи оператор сверяет с первичным источником:

1. точное название программы и провайдера;
2. официальный HTTPS-адрес программы и адрес перехода;
3. полную стоимость, а не размер ежемесячного платежа;
4. дату окончания акции, если указана акционная цена;
5. длительность, нагрузку, формат поддержки и расписание;
6. открытый, постоянный, закрытый или неизвестный статус набора;
7. аудиторию, prerequisites и заявленные цели;
8. значение `checked_at` и `price_checked_at` на момент фактической проверки.

Домены `source` и `offers[].url` должны присутствовать в `approved_domains`. Партнёрская ссылка не должна менять порядок выдачи или скрывать официальный источник.

## 4. Структурная валидация

Валидация не требует подключения к базе. `--no-deps` не запускает PostgreSQL и API:

```sh
docker compose run --rm --no-deps \
  --volume "$CATALOG_FILE:/data/catalog.json:ro" \
  api catalog validate /data/catalog.json
```

Ожидаемый результат:

```text
valid: <количество> courses
```

Любая ошибка о неизвестном поле, повторяющемся идентификаторе, домене, дате, цене или enum блокирует публикацию. Файл исправляется у источника данных и валидируется заново; отключать проверку запрещено.

## 5. Резервная копия

Создайте каталог, недоступный из web-контейнера, и снимок базы:

```sh
mkdir -p backups
chmod 700 backups
backup="backups/devcourse-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose exec -T db sh -c \
  'pg_dump --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" --format=custom' \
  >"$backup"
test -s "$backup"
chmod 600 "$backup"
printf 'Backup: %s\n' "$backup"
```

Если переменные не экспортированы в текущую оболочку, используйте значения из защищённой production-конфигурации. Не подставляйте демонстрационные пароли.

## 6. Обязательный dry-run

Dry-run подключается к текущей базе, берёт тот же advisory lock и читает существующий каталог, но завершает транзакцию без записи:

```sh
docker compose run --rm \
  --volume "$CATALOG_FILE:/data/catalog.json:ro" \
  api catalog import /data/catalog.json --dry-run | tee /tmp/devcourse-import-dry-run.log
```

Оператор проверяет каждую строку `add` и `update`, отдельно обращая внимание на:

- неожиданную смену `published` на `draft` или `archived`;
- резкое изменение цены;
- смену провайдера, языка или направления;
- исчезновение тарифа: для включённой в файл программы пропущенный тариф будет закрыт;
- неожиданно большое число изменений.

Отсутствующие в импортируемом файле программы не удаляются автоматически. Для снятия программы передайте её явно со статусом `archived`.

## 7. Публикация

После сохранения и проверки dry-run лога запустите ту же команду без флага:

```sh
docker compose run --rm \
  --volume "$CATALOG_FILE:/data/catalog.json:ro" \
  api catalog import /data/catalog.json
```

Импорт выполняется в одной транзакции. Ошибка в любой записи должна завершить команду ненулевым кодом и откатить изменения всей операции. Не повторяйте импорт до выяснения причины ошибки.

## 8. Проверка после публикации

Проверьте готовность API и общий ответ каталога:

```sh
curl --fail --silent --show-error http://localhost:8080/health/ready
curl --fail --silent --show-error \
  'http://localhost:8080/api/v1/courses?page_size=48' > /tmp/devcourse-courses.json
```

Затем вручную проверьте минимум:

1. один бесплатный и один платный тариф;
2. по одной программе каждого изменённого языка;
3. фильтр по цене и поддержке;
4. страницу или API-ответ одной изменённой программы;
5. сравнение двух изменённых тарифов;
6. `/out/{offer_id}` для одного предложения.

Импорт должен быть виден не позднее 60 секунд. Если проверка не пройдена, остановите публикацию и переходите к разделу восстановления.

## 9. Аудит операции

Убедитесь, что успешный импорт записан с ожидаемым оператором:

```sh
docker compose exec -T db sh -c \
  'psql --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" --command \
  "SELECT id, created_at, operator FROM imports ORDER BY id DESC LIMIT 5;"'
```

Сохраните вместе с release-артефактами:

- SHA release commit;
- контрольную сумму файла (`sha256sum "$CATALOG_FILE"`);
- путь и контрольную сумму резервной копии;
- dry-run лог;
- идентификатор записи импорта;
- результат ручной проверки.

Все значения и ссылки на перечисленные артефакты внесите в протокол публикации. Протокол должен однозначно связывать каталог, backup, dry-run, импорт и ручную проверку с одним release commit.

## 10. Восстановление

Ошибочный успешно завершённый импорт не следует исправлять прямыми `UPDATE` в production. Подготовьте исправленный каталог и повторите полный процесс, если приложение остаётся работоспособным.

Если требуется полное восстановление снимка, сначала остановите запись в приложение и подтвердите выбранный backup. Восстановление выполняется в отдельную пустую базу или в рамках утверждённой процедуры эксплуатации; пример для локального стенда:

```sh
docker compose stop api frontend
docker compose exec -T db sh -c \
  'dropdb --username "$POSTGRES_USER" --if-exists "$POSTGRES_DB" && \
  createdb --username "$POSTGRES_USER" "$POSTGRES_DB"'
docker compose exec -T db sh -c \
  'pg_restore --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" --clean --if-exists' \
  <"$backup"
docker compose up -d api frontend
curl --fail --silent --show-error http://localhost:8080/health/ready
```

Для production конкретные команды должны учитывать управляемый PostgreSQL, права ролей и политику остановки трафика. После восстановления повторите проверки раздела 8 и зафиксируйте инцидент.

## 11. Чек-лист публикации

- [ ] Источники, цены, даты и набор проверены оператором.
- [ ] `CATALOG_OPERATOR` задан и не равен `local-operator`.
- [ ] `catalog validate` завершился успешно.
- [ ] Создана и проверена непустая резервная копия.
- [ ] Dry-run лог просмотрен и сохранён.
- [ ] Импорт завершился с кодом 0.
- [ ] Health, выдача, фильтры, сравнение и переход проверены.
- [ ] Запись аудита содержит ожидаемого оператора.
- [ ] SHA и контрольные суммы сохранены.
- [ ] При необходимости выполнено и проверено восстановление.
- [ ] Протокол публикации заполнен, подтверждён оператором и сохранён с release-артефактами.

## 12. Ежедневные резервные копии

Скрипт `scripts/backup-database.sh` создаёт атомарный custom-format dump с правами владельца и удаляет только свои завершённые копии старше семи дней. Пример задания cron на сервере (ежедневно, 02:00 UTC при UTC-часовом поясе сервера):

```cron
0 2 * * * cd /srv/devcourse-finder && ./scripts/backup-database.sh >> /var/log/devcourse-backup.log 2>&1
```

Путь адаптируется к серверу; установка cron на production и контроль неуспешных запусков выполняются оператором при развёртывании. Проверяйте восстановление в отдельную БД с суффиксом `_restore_test`, не поверх рабочей базы. Локальная проверка восстановления подтверждает формат копии, но не установку расписания на production.
