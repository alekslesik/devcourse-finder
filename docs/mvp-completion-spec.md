# Техническое задание: завершение MVP DevCourse Finder

## 1. Назначение документа

Документ определяет работы, необходимые для перевода текущего технического прототипа DevCourse Finder в состояние MVP, готового к ограниченному публичному запуску.

Базовые продуктовые правила, модель данных и исходные критерии приёмки описаны в [функциональных требованиях](./functional-requirements.md). Это ТЗ не заменяет их, а фиксирует оставшийся объём реализации, порядок проверки и единое определение готовности.

Актуальные статусы всех пунктов и оставшиеся проверки собраны в [единой таблице готовности](./mvp-readiness.md). «Реализовано» в описании пункта не означает, что пройдены слияние, CI и итоговая приёмка.

## 2. Исходное состояние

На момент подготовки ТЗ в репозитории уже есть:

- Go API с поиском, фильтрацией, сравнением, переходами к источникам и приёмом аналитических событий;
- PostgreSQL-схема, миграция, валидация и транзакционный импорт каталога;
- интерфейс Next.js с фильтрами, выдачей, карточкой в модальном окне и сравнением;
- Dockerfile для API и frontend, Compose-стек с PostgreSQL и одноразовой миграцией;
- модульные тесты основных правил каталога и CI-конфигурация сборки.

Текущее состояние считается прототипом, а не завершённым MVP: каталог при первом запуске пуст, отсутствуют отдельные публичные страницы программ и OpenAPI-контракт, не автоматизирован полный пользовательский сценарий.

## 3. Цель этапа

Результатом этапа должна стать версия, в которой посетитель без регистрации может:

1. открыть сайт на компьютере или телефоне;
2. подобрать обучение по языку, опыту, цели, бюджету и дополнительным параметрам;
3. открыть отдельную страницу программы с актуальными условиями;
4. сравнить до трёх тарифов по постоянной ссылке;
5. безопасно перейти на официальный или партнёрский сайт источника.

Оператор должен иметь возможность проверить и транзакционно импортировать каталог. Новый стенд должен разворачиваться одной документированной Compose-командой, проходить автоматические проверки и содержать демонстрационные данные для проверки сценария.

## 4. Объём работ

### 4.1. Каталог для демонстрации и приёмки

#### MVP-DATA-01. Импортируемый набор данных

**Статус реализации:** выполнено. Набор находится в `data/demo-catalog.json`, а его валидность и обязательное распределение проверяются тестом пакета `catalog`.

Добавить отдельный JSON-файл демонстрационного каталога, соответствующий действующей схеме импорта.

Требования к набору:

- не менее 20 программ: минимум по 5 для Go, Python, Java и JavaScript;
- представлены бесплатные и платные предложения;
- представлены самостоятельные форматы, проверка заданий и наставничество;
- представлены профили для новичков и разработчиков с опытом;
- у каждой программы заполнены источник, дата проверки, аудитория, цели и хотя бы один тариф;
- вымышленные записи явно имеют `demo: true` и не выглядят как реальные предложения школ;
- все внешние адреса используют HTTPS и входят в `approved_domains`;
- файл проходит команду `catalog validate`.

Демонстрационные данные не должны автоматически попадать в production-базу при каждом запуске контейнеров. README должен содержать отдельную команду их явного импорта.

#### MVP-DATA-02. Проверяемый production-процесс

**Статус реализации:** выполнено. Команды валидации, dry-run и явного импорта приведены в README, а проверка источников, резервное копирование, аудит, публикация и восстановление описаны в `docs/catalog-operations.md`. Импорт требует явный идентификатор `CATALOG_OPERATOR`. Результат каждой production-публикации фиксируется по шаблону `docs/catalog-publication-record.md`; заполненная запись является подтверждением выполнения процесса оператором, а не частью исходного кода.

Описать процедуру подготовки реального каталога:

1. проверить источник, цену, формат и статус набора;
2. выполнить `catalog validate`;
3. выполнить импорт с `--dry-run`;
4. проверить список изменений;
5. выполнить импорт без `--dry-run`;
6. проверить выдачу и исходящий переход.

### 4.3. Контракт API

#### MVP-API-01. OpenAPI

**Статус реализации (03.10.2026):** Добавлен `docs/openapi.json` (3.1), в CI подключены валидация и консервативная проверка совместимости с целевой веткой. Валидатор проходит; HTTP-тесты общего production-handler проверяют ответы публичных маршрутов по схемам OpenAPI, включая реальные запросы с PostgreSQL.

Добавить версионируемый OpenAPI 3.1 контракт для всех публичных маршрутов:

- `GET /api/v1/catalog/options`;

Контракт должен описывать параметры, перечисления, ограничения, успешные ответы и единый формат ошибок. CI должен проверять синтаксис контракта и несовместимые изменения.

#### MVP-API-02. Согласованные типы

**Статус реализации (03.10.2026):** Типы frontend генерируются из OpenAPI в `frontend/lib/api.generated.ts`; CI проверяет отсутствие расхождения генерации.

#### MVP-API-03. Ошибки и наблюдаемость

**Статус реализации (04.10.2026):** Проверено локально: машинные HTTP-коды, request_id и безопасные JSON-ошибки проверяются по OpenAPI. CLI записывает безопасные JSON-диагностики с command, run_id, stage и code; при необходимости — SQLSTATE, известное ограничение, индекс записи или JSON-offset. Настоящий CLI entry point проверен в отдельных OS-процессах с PostgreSQL 17: exit 1 и rollback каталога/доменов/ревизии при SQL-ошибке, отказ подключения, валидация, dry-run и успешное обновление цены. Тесты подтверждают отсутствие тестовых секретов и полных URL в выводе. Raw-ошибки драйвера и декодера не журналируются; блок слит в [PR #15](https://github.com/alekslesik/devcourse-finder/pull/15), CI прошёл.

Все API-ошибки должны возвращать JSON с машинным кодом и безопасным сообщением. Запросы должны получать `request_id`, а структурированные логи не должны содержать секреты и полные пользовательские URL.

Неуспешный импорт должен завершаться ненулевым кодом, не менять каталог и оставлять диагностируемую запись в журнале приложения.

## 5. Что не входит в MVP

- пользовательские аккаунты и авторизация;
- приём платежей, корзина и заявки в школы;
- отзывы и пользовательские рейтинги;
- личный кабинет школы и веб-админка;
- автоматический парсинг сайтов и партнёрские API;
- AI-консультант и персонализация на основе ML;
- полнотекстовый поисковый кластер;
- автоматическая конвертация валют.

Добавление этих функций не должно задерживать выполнение требований раздела 4.

## 7. Критерии готовности MVP

MVP считается готовым только при одновременном выполнении всех условий:

- [ ] требования MVP-DATA, MVP-WEB, MVP-API, MVP-NFR, MVP-QA и MVP-OPS выполнены либо имеют явно согласованное исключение;
- [ ] все AC-01—AC-20 из функциональных требований пройдены и результат зафиксирован;
- [ ] основной CI для текущего release commit зелёный;
- [ ] Compose smoke test проходит с чистого checkout;
- [ ] демонстрационный каталог валиден и импортируется без ручного изменения файла;
- [ ] production-каталог содержит минимум 20 проверенных программ;
- [ ] выполнена ручная проверка на ширине 360 px и с клавиатуры;
- [ ] нет известных ошибок, блокирующих поиск, сравнение или внешний переход;
- [ ] подтверждено восстановление базы данных из резервной копии;
- [ ] README содержит актуальные команды запуска, импорта, проверки и остановки;
- [ ] статус README изменён с `MVP implementation is in progress` на готовность к ограниченному публичному запуску.
