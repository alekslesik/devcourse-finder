# Производительность поиска — MVP-NFR-04

## Методика

Воспроизводимый запуск: `./scripts/load/run.sh`. Подробности и параметры описаны в [инструкции стенда](../scripts/load/README.md). Для повторения в GitHub Actions предусмотрен ручной workflow `Search load test`.

- Production Go API и PostgreSQL 17, без fixture API и без кеша HTTP-ответов.
- 10 000 опубликованных синтетических предложений, по одному на программу; число проверяется SQL после валидированного импорта.
- API и PostgreSQL используют общий набор CPU `0,1`. Суммарные лимиты памяти — 4 GiB: API 1 GiB, PostgreSQL 3 GiB; дополнительный swap запрещён.
- 20 параллельных HTTP-клиентов, keep-alive, 12 вариантов query: широкий поиск, языки, сортировки, бюджет, поддержка, нагрузка, расписание, набор, совмещённые фильтры и пагинация.
- 60 секунд прогрева, затем 300 секунд измерения. p95 считается методом nearest rank по успешным ответам; время включает чтение полного тела. Любая ошибка проваливает проверку.

Стенд ограничен контейнерами на общем хосте, а не выделенной VM. Генератор находится вне лимитов API/БД. Замер проверяет поиск при 20 одновременно работающих клиентах (closed-loop); он не задаёт гарантию при произвольной частоте входящих запросов. Frontend-прокси, TLS и интернет-задержки не входят в этот замер.

## Выявленная проблема и изменение

Диагностический запуск до изменения: 10 секунд прогрева и 20 секунд измерения, p95 **1367,4 мс**, 354 успешных запроса, ошибок нет. Это короткий замер для диагностики, не результат приёмки по ТЗ.

Каждый поиск загружал из PostgreSQL все программы и тарифы в отдельной транзакции. Теперь API хранит неизменяемый снимок каталога и на каждом запросе проверяет последнюю успешно зафиксированную ревизию в таблице импорта. Новый CLI-импорт инвалидирует снимки во всех процессах API. Холодная загрузка и обновление снимка сериализованы; версия и данные читаются в одной repeatable-read транзакции. Параметры поиска, цены и сроки действия по-прежнему рассчитываются для каждого запроса.

Сбой БД не скрывается кешем: запрос версии должен пройти, иначе API возвращает 503. Поддерживаемый путь публикации — транзакционный импорт; прямые SQL-правки каталога обходят механизм ревизий. После восстановления БД из резервной копии процессы API следует перезапустить.

Обновление цены через импорт и отказ БД проверяются настоящими HTTP-запросами с PostgreSQL. Тесты также проверяют конкурентные чтения, сохранность старого снимка и отсутствие инвалидирования после rollback; race detector проходит.
